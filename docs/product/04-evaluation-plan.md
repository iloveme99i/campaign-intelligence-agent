# 评测与上线门槛

## 1. 评测目标

评测不是判断回答“像不像专家”，而是确认 Agent 是否在正确口径、正确顺序和真实证据上完成可行动复盘。

## 2. 离线确定性门槛

`score_trace` 当前对持久化事件执行 41 项硬检查。以下按能力域归纳，而不是把实现键逐条复述：

1. 存在用户确认的 `scope_id`。
2. `compare_periods` 先于文字答案。
3. 查询结果未截断。
4. 本轮数字不混用多个 scope。
5. 最终答案存在。
6. 引用的 `evidence_id` 均来自真实工具结果。
7. 覆盖目标结果、用户路径、成本和下一轮动作。
8. 明确区分已确认事实、解释假设和待验证项。
9. 下一轮行动包含验证指标、护栏指标和继续/停止条件。
10. 明确前后比较与因果结论的边界。
11. 结构化任务触发了定向诊断，且诊断发生在最终答案之前。
12. 诊断理由被记录，选择的维度与优先风险或明确业务限制相符。
13. 一轮只下钻一个必要维度，避免无目的遍历。
14. 诊断证据被最终答案引用，诊断 `scope_id` 与总盘口径一致。
15. 目标、总盘和诊断数字在结论层同样带证据，不能只在事实附录补引。
16. 不使用“必然”“一定”“会提升”等未经实验或预测模型支持的前瞻表述。
17. 目标达成但贡献下降时，结论必须正面呈现经营张力。
18. `path_buyer_users = buyer_users` 不能被误写为“完成关键行动到购买没有断点”；路径阶段仍按 `path_buyer_users / activated_users` 核对。
19. 只在某一既有方案内随机新动作时，对照必须来自同一合格人群内的原动作，不得把另一个历史方案冒充随机对照。
20. 回答中的百分点差必须与同行展示的两个比率算术一致。
21. 置信区间与 p 值只归属于工具声明的 `purchase_per_exposure` 指标，不得挂到激活后路径购买率上。
22. 当确定性 `path_diagnostics` 已给出最低承接节点时，回答必须按实验组与该节点一致；多组节点不同时不得合并成一个“全局瓶颈”。
23. 净收入、贡献额、优惠、退款与活动成本从整数分转换为元后，必须落在对应两期或全活动金额包络内；原始分值直接标成元时硬失败。
24. 每个带业务指标标签的元金额，必须能在确定性工具证据中找到对应原值、合法两期差额或成本合计；“有引用但数字写错”同样硬失败。
25. 商家可见结论不得泄漏 `decision_ready`、`descriptive_signal`、`scope_id` 等内部字段名，必须翻译成业务判断。
26. 引用合格 DiD 时，必须说清 ATT 是“每个处理经营单元的活动后周期均值，相对活动前周期均值的平均处理效应”，不得冒充整场活动总增量。
27. 当前期周期太少且前趋势检验力低时，必须对商家明示“未拒绝不等于证明平行趋势”，不能只写“检验通过”。
28. 商家可见回答不得暴露以“分”为单位的原始金额；金额必须先按数据契约转换为元。
29. 回答必须直接解决用户本轮的继续、调整、放大或停止意图，并给出成立条件，不能只输出通用分析。

增量识别另有方法级测试，不把一段模型文案当作因果验证：平衡面板与稳定处理身份是硬前置；处理与对照各少于 4 个经营单元时直接拒绝估计；已知 ATT 的合成面板必须复原真值；主效应与安慰剂使用 Welch–Satterthwaite 小样本 t 推断，前趋势使用有限自由度。非平行前趋势、活动前伪效果或未审查干扰任一出现，结果必须降级为不可作因果解读。存在合格 DiD 时，回答需引用其独立证据并交代 ATT 与识别假设；不存在或验证失败时，原有伪因果门禁继续生效。

其中任一失败，该场景不通过；不以平均分掩盖关键错误。

## 3. DeepSeek 场景评测

`evals/merchant_review_cases.jsonl` 由脚本确定性生成 54 条场景，覆盖 3 类活动、4 种决策意图、4 类风险重点和 6 个带业务限制的过滤口径。配置真实 API Key 后，先单次跑完整矩阵定位失败簇；修复后对发布候选的核心场景各重复三次，记录：

- 工具选择是否符合“总盘后按需下钻”，且能根据显式运营限制改变诊断方向；
- 是否重复查询或无目的遍历维度；
- scope 改变后是否重新计算并撤销旧结论；
- 关键数字引用准确率；
- 首个确定性结果时间、完整回答时间、输入/输出 token 与估算成本；
- 失败类型与可复现 trace。

真实调用完成前，不填写通过率、延迟或成本数字；已执行的子集必须同时报告通过与失败，不能只挑选成功样本。

历史 DeepSeek 开发运行保留在 `evals/real-runs-*.json`，用于复现真实失败，不作为 54 场景矩阵已经通过的证明。`evals/smoke-suite-run-2026-09-15-v2.json` 记录了一条当前代码的真实 DeepSeek 烟测：36/36 硬门禁通过，2 次模型调用，29,629 tokens，11.037 秒，未触发质控补写。这是单条单次证据；当前尚未批量执行新矩阵，因此不声明通过率、稳定性或线上效果。

`evals/smoke-incrementality-2026-09-16.json` 记录了增量识别链路的一条真实 DeepSeek 烟测：四个业务指标均由 8 个处理、8 个对照、3 个活动前周期和 1 个活动后周期的合成平衡面板估计，主效应和安慰剂改用 Welch–Satterthwaite 小样本 t 推断，不再使用正态近似。新记录 `503b3542-018b-4613-9cfd-eef73b459680` 在运行时通过当时 39/39 硬门禁，同一持久化记录按当前代码回放为 41/41；2 次模型调用，35,591 tokens，10.706 秒，未触发补写。该回答与页面均明示：仅 3 个活动前周期意味着前趋势检验自由度与检验力都很低，“未拒绝”不是“已证明平行趋势”。该文件同时保存快照与口径指纹，仍然只证明一个合成场景的一次运行。

6 条代表性案例在相同代码与模型配置下连续保留了 `v3` 至 `v7` 五轮真实 DeepSeek 运行，通过数依次为 2/6、4/6、4/6、4/6、1/6。`v7` 共 23 次模型调用、346,900 tokens，主要失败集中在共享成本归属、百分点算术、最低承接节点复述、单一实验主指标和金额证据落地。它证明仅靠长 prompt 与事后补写存在明显随机波动，也推动项目把关键经营口径改为确定性决策契约。

补齐第三种实验主指标、确定性金额单位转换、共享成本边界和结构化决策契约后，此前持续失败的腾讯游戏路径案例连续 3 次真实 DeepSeek 运行均通过 41/41，见 `path-decision-contract-run-2026-09-16-v2.json` 至 `v4.json`。随后 `representative-suite-run-2026-09-16-v8.json` 的 6 条跨业务代表案例全部通过 41/41：12 次模型调用、208,960 tokens、0 次事后补写，平均完整时延 10.527 秒。它证明本轮确定性契约修复在一个代表集轮次内有效，但还不能外推为 54 条全矩阵通过率或线上稳定性；下一步仍需重复代表集并执行完整矩阵。

`evals/quality-repair-money-grounding-2026-09-16.json` 保留了一次真实数字失败及修复重放：原回答把对比期贡献额 3,933 元写成 3,393 元，进而把降幅 1,742 元写成 1,202 元，并把贡献额减活动成本的 903 元差额表达得像成本。确定性门禁将其拦在 37/38；修复器改为只提供按指标标注的原值、直接差额和成本分项，真实 DeepSeek 重放在一次证据内改写后通过 38/38。该重放不写回原会话，用于验证修复链路，不把失败历史伪装成首次就正确。

评测按最新用户轮次隔离证据；历史口径会保留在会话中，但不会与当前 `scope_id` 混合计分。真实运行后执行：

```bash
PYTHONPATH=backend/src .venv/bin/python scripts/score-merchant-trace.py <conversation_id>
```

完整矩阵 runner：

```bash
.venv/bin/python scripts/run-merchant-eval-suite.py           # 仅验证案例，不调用模型
.venv/bin/python scripts/run-merchant-eval-suite.py --execute # 真实运行并保存失败模式
```

## 4. 人工评审量表

每条回答由评审者按 0/1 判断：

- 结论是否先回答目标，而非复述所有表格；
- 路径判断是否指出具体节点与对比基准；
- 实验建议是否同时考虑统计不确定性和经营代价；
- 假设是否与事实分开；
- 下一轮动作是否包含对象、改变、观察指标和停止条件；
- 是否存在空泛口号、伪因果或未经证据支持的数字。

## 5. 发布标准

- 所有自动化测试、类型检查、生产构建和设计检测通过。
- 两个核心场景连续三次无 scope 混用、虚构证据或因果越界。
- 320px、375px 和桌面视口主流程可用。
- 使用真实商家数据前完成脱敏、授权和保留周期评审。
- 若真实模型表现未过门槛，项目只作为确定性活动分析产品演示，不宣称 Agent 已可生产使用。
