# 三分钟项目检查

## 先看什么

1. README 中的产品截图：配置任务、读取计算结果、核对诊断依据。
2. `sample_data/`：所有演示数据均可重新生成并通过导入校验。
3. `evals/quality-repair-money-grounding-2026-09-16.json`：保留原始错误和修复结果，而非只展示成功答案。

## 核心设计取舍

### 计算不交给模型

金额用整数分存储，由参数化只读查询统一计算。模型负责选择调查方向、解释结果，不负责重新定义公式。原因是真实模型回归中发生过金额单位泄漏和数字转录错误；仅要求模型“认真核对”不足以稳定处理。

### 查询范围和分析任务分开

用户确认日期、渠道、人群、经营点及退款口径；Agent 在这个范围内选择调查方向。任务可以是调整、继续、扩大或停止，但不能因此偷偷改变取数范围。范围变更时重新计算并保留历史记录。

### 每个关键数字保留出处

查询证据包含 SQL、参数、数据快照和指标版本。页面把计算结果和模型判断分开展示，便于发现“数字正确但解释错误”。检查通过不等于专家确认业务结论正确。

## 三类具体错误

| 问题 | 原因 | 修改 | 验证 |
|---|---|---|---|
| 贡献额3933元被写成3393元 | 模型转录错误；原始返回内容缺少清晰的指标对应关系 | 按指标返回两期值和直接差额，核对回答后返回错误项重写 | 原失败保留；一次真实模型重放通过当时38项检查 |
| 完整路径购买者等于全部购买者，被解释成行动后没有损耗 | 混淆购买者路径完整性和行动到购买的转化率 | 独立返回各阶段人数、相邻承接率及最低承接节点 | 路径查询测试和模型失败样例回归 |
| 共享费用被归给单一渠道或人群 | 输入成本没有该维度明细，模型仍试图分摊 | 返回费用归属边界；无法归属时不计算该范围投入效率 | `test_engine.py` 的成本反例及回答检查 |

## 评测数字如何读

54条是开发场景集合，不是54条线上用户案例。41项是自动检查，不是人工事实正确率。
6条代表场景最新一轮通过检查，但此前多轮存在失败；详细记录保存在 evals 中，不宣称稳定通过率或真实业务提升。

## 来源和贡献范围

DataHub analytics-agent 提供通用会话、流式执行、LangGraph基础和模型连接。本项目新增活动数据契约、统一核算、任务和取数范围、诊断工具、证据展示及领域评测。
这是个人产品实践，不涉及模型训练；项目新增范围不等同于全部代码由一个人手写。产品负责人应能解释以上设计和实际取舍，不以提交作者字段代替能力证明。
