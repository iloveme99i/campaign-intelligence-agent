# 项目贡献边界与可验证证据

这份文档用于说清项目基线、领域重构和当前完成度。它不将上游能力冒充为个人开发，也不用代码行数代替产品判断。

## 1. 保留的上游基线

项目基于 `datahub-project/analytics-agent` Apache-2.0 代码基线（提交 `466e8ab3db967450db9578c7f649925f96e3de8c`）。保留的通用能力主要包括 FastAPI + React 应用壳、会话事件存储、SSE 流式执行、LangGraph 工具调用基础和可配置模型连接。

## 2. 新增的领域闭环

| 问题 | 项目新增的处理 | 可验证位置 |
|---|---|---|
| 通用问数没有经营任务边界 | 结构化 `ReviewTask`：决策意图、优先风险、业务限制与 `task_id` | `merchant/scope.py`、首页任务单、导出记录 |
| 模型可能自行改口径 | 冻结 `ReviewScope`，口径哈希化，变更后新建证据轮次 | `merchant/scope.py`、`ScopeEditor.tsx` |
| LLM 心算关键数字不可靠 | 目标、两期结果、路径、实验和成本先由参数化只读工具计算 | `merchant/engine.py`、`target.py`、`experiment.py` |
| 切换日期后路径和成本仍沿用整场数据 | 指标版本 v0.8：订单、顺序路径、定向诊断和成本统一按已确认活动期查询；活动结束后配置窗口内的曝光关联订单单列 | `merchant/scope.py`、`merchant/engine.py`、`test_scope.py` |
| 跨人群的独立节点相减被误称“流失” | 同一匿名用户的曝光、访问、领取、行动与购买按事件时间串联；另保留活动标签下全部购买者，不能与完整路径购买混用 | `merchant/scope.py`、`ReviewSnapshot.tsx`、`test_scope.py` |
| 仅展示总量掩盖时间和分层异常 | 同一口径返回逐日/逐周两期趋势、实验组/渠道/经营点/人群分层、可链接购买与跨组曝光质量读数，并持久化查询证据 | `merchant/engine.py`、`TrendAnalysis.tsx`、`SegmentMatrix.tsx`、`DataReliability.tsx` |
| 污染组和未链接购买者仍产生显著性或目标结论 | 对跨实验组曝光、无法链接先前曝光、购买数超过曝光数的情况停止检验或转化目标判断；历史指标版本不可落档 | `merchant/experiment.py`、`target.py`、`api/merchant.py` |
| 订单标签与曝光标签不一致仍计算分层转化率 | v0.7 按同一用户、先曝光后购买，核查订单的实验组、渠道、经营点与人群标签；不匹配的分层比率在页面隐藏，诊断与实验测算停止。双维交集要求两种标签在同一次先前曝光中同时匹配 | `merchant/scope.py`、`api/merchant.py`、`SegmentMatrix.tsx`、`test_scope.py` |
| 尾窗订单只按同一用户匹配曝光，可能跨渠道误计 | v0.8 逐笔订单寻找活动期内同用户、同实验组/渠道/经营点/人群的先前曝光，再应用归因天数；匹配不上不列入尾窗观察值 | `merchant/scope.py`、`test_scope.py` |
| 没有记录的日期被当成“零经营”或“导出完整” | 同口径统计对比期有订单、活动期有订单和曝光的日数；缺行提示核对导出，日期全有记录也不声称导出完整，最后观察订单日不冒充数据截止日 | `merchant/scope.py`、`DataReliability.tsx`、`test_scope.py` |
| 分组汇总把同一用户跨维度重复相加 | 按当前诊断维度直接对原始匿名事件做去重聚合，而不是求和预聚合漏斗 | `merchant/scope.py`、`test_scope.py` |
| 筛人群或单一实验组后成本归属被误判 | 共享费用与缺少经营点/人群粒度的费用标为不可分摊，不计算该范围的投入效率 | `merchant/engine.py`、`test_engine.py` |
| 总盘后只让模型总结，不算真正 Agent | 模型先接收多维扫描，再按决策任务和业务限制选择最多三项不重复的定向复核；理由、证据和停止边界可追踪 | `merchant/engine.py`、`runtime.py`、`DiagnosticTrail.tsx` |
| 结论与数字无法互证 | 每次查询生成 `evidence_id`，回答引用真实证据编号 | `merchant/readonly.py`、`ReviewSnapshot.tsx` |
| 页面只露出总盘数，诊断过程不易核对 | 展示分组顺序路径、日均订单、单均经济性，并用对称恒等式拆开日均贡献额中的订单规模项和单均贡献项；算术项不冒充原因归因 | `DiagnosticReadout.tsx`、`ReviewSnapshot.tsx` |
| 路径表有节点数字，但仍要人工找主要断点 | 后端按每个实验组的相邻阶段承接率确定性标记最低承接节点，同时给出未进入下一步的人数；明确它只是调查优先级，不冒充可恢复增量或原因 | `merchant/journey.py`、`ReviewSnapshot.tsx`、`test_journey.py` |
| 复盘只产生一篇文字 | 事实/假设/待验证/行动分层，并将负责人与复查日期绑定到口径及回答摘要 | `DecisionRecord.tsx`、`api/merchant.py` |
| 下一轮方案没有可执行的实验规模 | 用户明确选择实验对象/分组和购买或领取后激活指标，后端从已保存的完整分层证据提取单维群体；双维交集从同一不可变快照按已确认口径重新查询，绝不相乘边际人数。连同 MDE、流量比例计算样本量与周期，落档时再计算并绑定快照与交集范围；未完成分层扫描则拒绝测算 | `api/merchant.py`、`merchant/experiment.py`、`ExperimentPlan.tsx` |
| 主指标分母可能受干预影响 | 实验规划把“分母资格早于干预”列为上线前必验条件；若入口或承接页调整会改变谁进入激活人群，不能把激活后购买率作为该干预的实验主指标 | `merchant/runtime.py`、`merchant/experiment.py` |
| Agent 建议落档后没有结果验证，无法知道建议是否有效 | 复查节点记录执行状态、测量设计、两组样本、护栏与数据来源；后端确定性检查预设样本量、SRM、显著性、95% 区间和 MDE，非随机对比只保留为方向性信号 | `api/merchant.py`、`merchant/experiment.py`、`OutcomeReview.tsx` |
| 修改日期或筛选后旧结论仍可能被误用 | 确定性比较前后口径与活动期指标，旧结论及旧落档决策显式失效，不让模型自行解释改口 | `merchant/revision.py`、`ScopeRevisionNotice.tsx` |
| “看起来对”但无法回归 | 41 项 trace 质量门检查工具顺序、口径、证据、数字引用、原始金额单位泄漏、金额与证据值、路径阶段与断点、实验对照、指标血缘、决策意图、ATT 估计对象与前趋势检验力边界、内部字段泄漏、成本归属与因果边界；未通过不能直接决策落档。单位转换与共享成本语义先由确定性契约归一化，其余失败最多执行两次证据内修复；每次调用单独记录 token，仍未全过则不发布 | `merchant/evaluation.py`、`merchant/quality_repair.py`、`TraceAudit.tsx`、`evals/` |
| 前后变化无法回答真实增量 | 增加可选同期经营单元面板，执行平衡面板 DiD、前趋势、活动前安慰剂与干扰审查；失败时强制降级为不可因果解读 | `merchant/incrementality.py`、`merchant/importer.py`、`ReviewSnapshot.tsx`、`test_incrementality.py` |
| Agent 建议缺少业务反馈闭环 | 决策落档区分按建议执行、修改后执行与暂不采用；记录原因、最终动作和落档时质量门。失败回答可被驳回留样，但不能被采纳 | `api/merchant.py`、`DecisionRecord.tsx`、`merchant/report.py` |

## 3. 当前验证

- 商家领域测试覆盖导入校验、只读约束、口径继承、目标计算、实验边界、trace 评测、导出与决策落档。
- v0.8 以前的记录在页面标为历史口径；重新核算前不允许实验规划或决策落档。
- 2026-09-11 至 09-12 保留 12 次真实 DeepSeek 调用。腾讯游戏口径修订案例曾通过当时的 26/26 门槛；后续门槛升级后，旧回答中“随机分流未验证且 p=0.078，却直接迁移入口曝光”的建议被正确标为未通过。它仍是历史失败样本，不能声称已通过当前门槛或可直接执行。
- 2026-09-14 在重新生成的合成案例上，真实 DeepSeek 调用完成腾讯零售全期复盘；早期运行曾通过当时的 27/27、29/29 门槛。门槛后续继续升级，因此历史满分不等于通过当前 33 项规则。这些是开发期回归，不构成总体可靠性或线上效果证明。

## 4. 不应被夸大的部分

- 目前没有真实商家访谈、可用性测试或线上对照结果。
- 当前是单用户本地版，不等于已交付的企业级权限与数据产品。
- 真实模型评测只有开发期小样本，不能表述为稳定通过率。
- 活动结束后的曝光关联订单按配置窗口单列，缺少快照数据截至时间和随机对照，不支持宣称尾窗已最终结算或存在因果增量。
- 满分是确定性格式与部分决策边界门槛，不是人工核验事实正确率；仍需用不同业务数据做盲测、人工复核和失败样本分析。没有导出截至时间时，尾窗 0 单不能被解释为最终无延迟转化。2026-09-14 的一次真实模型回答将逐日优惠分值误写成元，原有 27 项审计未检出；加入非负优惠的总额上界校验后被拦下。另一次回答同时列出两种实验主指标，被新增的单指标检查拦下。这两类失败保留为回归测试；本轮重复的开发期记录已清理，保留一条通过当前审计的新记录。较早历史案例仍需按当前门槛分别审阅。

## 5. 面试可展开的决策

1. 为什么把“复盘任务”与“查询口径”分成两个对象，而不是都放进 prompt。
2. 为什么让确定性工具先算、Agent 后解释，以及这对 trace 评测有什么影响。
3. 为什么保留失败的真实模型记录，而不只展示通过样例。
4. 为什么决策落档同时绑定 scope 和回答摘要，而不允许旧决策被新回答覆盖。
5. 为什么评测不把“成本风险”机械映射到实验组，而会在商家明确提出缺货时允许 Agent 改查经营点。
6. 为什么实验样本量由已保存证据确定性计算，但 MDE 必须由业务负责人确认。
7. 为什么口径变化后系统直接撤销旧结论的适用性，而不是要求模型判断自己是否需要改口。
