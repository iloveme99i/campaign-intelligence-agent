# 公开机制原型与跨业务评测

## 1. 为什么不是一个“夏日促销”示例

只有单一券活动时，即使回答流畅，也无法判断 Agent 是否真正理解业务任务，还是记住了固定分析套路。当前合成快照放入三个结构不同的活动，用它们检验同一套 Agent 能否在共享证据契约上选择不同的诊断路径。

所有明细和结果数字均由 `merchant/examples.py` 确定性生成。公开资料只用于理解机制，不采集企业内部数据，不复刻品牌视觉，也不声称示例结果来自字节跳动或腾讯。

## 2. 三个机制原型

| 原型 | 公开机制依据 | 合成场景里的决策张力 | 主要诊断维度 |
|---|---|---|---|
| 字节系 · 全域大促 | 抖音电商公开大促包含活动报名、立减/直降、平台补贴与多场域曝光；官方学习平台同时区分短视频、直播、商城、达人与数据运营 | 两种承接方案的转化、客单、商家优惠、平台优惠和投放成本不同，不能只按成交率扩量 | 方案、渠道、成本 |
| 腾讯游戏 · 回流任务季 | 腾讯游戏公开活动常见回流人群、每日/每周/累计任务、阶段奖励和领取条件 | 一次性登录礼进入率更高，分阶段任务的关键行动和后续交易更强，但激励成本也更高 | 方案、人群、服务区 |
| 腾讯智慧零售 · 私域联动 | 腾讯智慧零售公开材料描述广告/公众号引流、小程序承接、发券、支付和再次触达链路 | 单独发券与“内容 + 券”在领取、关键行动、收入与活动成本间存在权衡 | 渠道、人群、方案 |

## 4. 面试时必须守住的事实边界

可以说：基于公开机制设计了跨业务合成评测集，用于检验 Agent 的事件标准化、工具选择和因果边界。

不能说：复盘过字节或腾讯的真实活动、接触过其内部数据、得出了这些公司的真实经营结论。项目含金量来自问题建模和可验证系统，不来自借用公司名称。
